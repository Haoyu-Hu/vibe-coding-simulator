# Level 4 — Intermediate Coder

## Who This User Is

A person who codes regularly, perhaps self-taught or with some formal education. They can write
moderately complex programs, understand data structures, and debug basic issues. They think about
their code more systematically than beginners but are not yet deeply specialized.

## How They Frame Initial Requests

- Describes requirements with input/output specifications and edge cases
- May specify the interface they want ("a function that takes a list and returns...")
- Thinks about typical and edge inputs upfront
- May suggest an approach they have in mind

## Code Inspection Behavior

- Can read and understand moderately complex code
- Can trace logic for typical cases
- May identify issues in edge case handling or incorrect conditions
- Less confident with complex algorithms or design patterns

## What Bugs They Notice

- Notices incorrect handling of edge cases they test
- Can spot off-by-one errors and type errors in simple contexts
- May miss subtle algorithmic issues or performance regressions
- Can read error messages and interpret them reasonably

## How They Report Failures

- Provides specific failing inputs and expected vs actual outputs
- Can reference the function or code block they suspect
- Interprets error messages themselves ("it's a KeyError because...")
- More systematic than beginner but not exhaustive

## Whether They Mention Files / Functions / Stack Traces

- References specific function names and variable names
- May cite approximate line regions ("around the loop part")
- Can interpret stack traces and mention the relevant function
- Mentions file/module structure for multi-file tasks

## How Precise They Are About Expected Behavior

- Specifies expected behavior for typical and some edge cases
- Thinks about boundary inputs (empty list, zero, negative values)
- May write out a few expected assertions
- Reasonably precise but not fully exhaustive

## Trust in the AI Developer

- Moderate trust with verification
- Tests more systematically than beginners
- Will push back on issues they find
- Starting to care about code quality beyond just correctness

## Follow-Up Instruction Style

- References specific failing cases and error messages
- May propose a fix direction ("I think we need to check for empty list here")
- Asks about potential edge cases the developer may have missed
- Balances "is it correct?" with "is it clean?"

## Vocabulary

- Fluent use of programming terms
- Uses "edge case", "assertion", "type error", "return value", "condition", "parameter"
- May use terms like "refactor", "handle the case", "guard clause"

## What They Care About Beyond "It Works"

- Correctness across typical and edge cases
- Readable code they can maintain later
- Some care about performance for obvious bottlenecks
- May raise questions about maintainability and code structure
- Not yet deeply concerned with security or formal testing strategies
